# 安全模型

这个工具的价值不在于「跑出一份清单」，而在于**每条结论都能被追问到原始证据**。
本文说明信任是怎么分级的、失败时是什么语义、以及哪些事情工具明确不做。

## 一、信任分级

| 级别 | 判定依据 | 适用源 |
| --- | --- | --- |
| A | 每份发布物都有厂商分离签名，且签名者指纹与代码里固化的值一致 | Red Hat CSAF、SUSE CSAF |
| B | 只有 HTTPS 传输 + 哈希自校验 | Debian、Ubuntu、Alpine、Arch |

A 级不是「更可信所以更好看」，而是**可追责**：签名通过意味着「这份字节确实由厂商私钥签发」，
HTTPS 与 SHA256 只能证明「传过来的时候没坏」，不能证明来源。

实现上的三条硬约束：

1. **指纹固化在代码里**。Red Hat 取自 `provider-metadata.json` 声明的值，
   SUSE 从其官方公钥文件现场算出后写入常量。运行时绝不接受「谁签的都行」，
   否则拿到任意一把密钥就能冒充厂商。
2. **指纹不符立即失败**，不降级、不告警后继续。换钥必须改代码并走一次发布，
   这是有意为之的成本。
3. **没有验签器就拒绝写库**。A 级源在未配置验签器时直接报错，
   「先写进去以后再验」等于把未验证数据标成厂商数据。

B 级源的 `signature_status` 记为 `not-applicable`，不是 `verified`——
把两者混为一谈会让报告虚增签名覆盖。

## 二、签名与完整性分列

数据库里 `feed_artifacts` 有两列：`signature_status` 与 `integrity_status`。

| 列 | 取值 | 含义 |
| --- | --- | --- |
| `signature_status` | `verified` / `failed` / `missing` / `unverified` / `not-applicable` | 厂商签名 |
| `integrity_status` | `verified` / `failed` / `unchecked` | 存入与读出时的哈希 |

两者正交：哈希通过而签名缺失是完全正常的状态（B 级源），
签名通过而哈希不符说明存储层出了问题——都必须能分别表达。

## 三、失败语义

统一原则：**失败不产生新结论，只保留旧结论并显式标出上一次成功的状态**。

| 场景 | 行为 |
| --- | --- |
| 抓取失败 / 5xx / 超时 | 该源标记 `error`，上一份有效快照继续生效 |
| 解析异常率超阈值 | 整批拒绝，不写半套数据 |
| 验签失败 | 该文档被丢弃并计入失败率；A 级源不会因此"降级为可用" |
| 数据库事务中途失败 | 事务回滚；`is_active` 指针只在提交时翻转 |
| 磁盘写入中断 | 内容寻址 + `tmp → fsync → rename`，不会留下半个文件 |

「半套情报」比「没有情报」更危险：前者会让覆盖状态看起来仍是 `COVERED`，
于是读者以为检查过了。

## 四、覆盖不足必须可见

扫描完成不等于结论可信。`scan` 计算整体覆盖状态：

| 覆盖 | 含义 | 退出码 |
| --- | --- | --- |
| `COVERED` | 全部已接入源都在有效期内且同步成功 | 0（无洞时） |
| `PARTIAL` | 部分源缺失或过期 | 9 |
| `UNKNOWN` | 没有任何可用源 | 9 |

退出码 9（`COVERAGE`）是本工具对 CI 最重要的设计：没有它，
**「什么都没查到」和「什么都没检查」在脚本里是同一个 0**。

## 五、判定规则的边界

- 版本比较使用发行版原生语义：`dpkg`（含 `~` 回移）、`rpm`（含 epoch 优先级）、
  `apk`、`pacman`。不做语义化版本近似。
- 弱证据（发布方未给修复版本，只有仓库当前版本）只能用于确认「已修复」，
  不能用于判定「受影响」。
- 同一包同时存在「不受影响声明」与「修复记录」时判 `UNKNOWN`：证据冲突不择一。
- 数据源未收录 ≠ 不受影响。只有发布方显式声明的不受影响才产出 `NOT_AFFECTED`。
- 生命周期不在支持范围内（EOL / Legacy / 未知）时，检测结论不变，
  但自动修复一律关闭。

## 六、自动修复的闸门

`fix` 只在同时满足下列条件时才会执行：

1. 目标 release 在支持矩阵中登记且 `AutoFix` 为真（首期只有 Debian 12/13）。
2. 包管理器可用，且不是滚动发行版（无固定版本语义）。
3. 当前进程是 root。
4. 命令行显式给出 `--yes`。
5. 该条判定是 `VULNERABLE` + `FIX_AVAILABLE`，且有明确的目标版本。

执行后必须复检：重新采集版本、按原生规则比较，复检不通过返回退出码 6
（`REMEDIATION_FAILED`）。工具不会自动重启服务器，涉及内核包时只提示需要重启。

## 七、明确不做的事

- 不评估 CVSS 与环境可利用性，不做风险打分。
- 不修改业务配置，不删除文件，不清理缓存。
- 不自动重启，不自动回滚（包升级本身不可回滚）。
- 不上传资产清单；所有判定在本机完成。
- 不把「本工具没报」当成安全证明。
